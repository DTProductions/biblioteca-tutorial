Como os tutoriais foram reproduzidos

Para cada UC, foi criado um diretório limpo a partir do commit original 0920d3b, aplicados somente os pacotes dos seus pré-requisitos transitivos e o próprio pacote, sem copiar os fontes diretamente do workspace.

Em cada uma das 23 cópias foram executados: conferência dos códigos e hashes, typecheck do backend, teste próprio do UC contra um banco PostgreSQL exclusivo e build do frontend. Isso verifica se um aluno consegue implementar sua atividade sem depender de arquivos de outro caso ainda não integrado.

Professor · reproduzir os 23 casos
python3 qa/replay-tutoriais.py

O script lê a configuração de conexão em seu próprio cabeçalho e aceita os argumentos documentados em --help. Execute contra um PostgreSQL de validação; ele cria bancos exclusivos cujo nome termina em _test.

Verificação no navegador

Os testes Playwright usam Chromium real e dados persistidos no PostgreSQL: cadastram, buscam, editam e excluem; reservam, cancelam, emprestam e devolvem; conferem limites e preservação do histórico. A documentação é aberta por HTTP para conferir todos os blocos de código, o botão de cópia e o layout em desktop e celular.

Professor · executar Playwright no ambiente isolado
docker compose -p biblioteca-uc22-validacao -f infra/compose.yaml -f qa/compose.yaml up -d --build
cd qa
bun install --frozen-lockfile
bunx playwright install chromium
PLAYWRIGHT_JSON_OUTPUT_NAME=evidencias/playwright.json bun run test -- interface.spec.ts regras.spec.ts

Os testes de documentação usam um servidor HTTP local na porta 62312, servido na raiz do repositório. Os testes de regras que alteram datas exigem a URL do banco de validação, conforme o arquivo de teste. Nenhum teste de escrita deve apontar para o banco de uso real da biblioteca.

Aula — Fila de mensagens e worker assíncrono

Cadastrar um livro hoje espera o Gemini gerar o embedding. Nesta aula, a requisição grava no Postgres, publica uma tarefa numa fila e responde na hora; um worker, outro processo com o mesmo código, consome a fila e atualiza o índice semântico. No caminho: Redis Streams com grupo de consumidores, confirmação, nova entrega, fila de mortas e por que toda tarefa precisa ser segura para repetir. 00

Antes de começar

Esta aula parte da branch saas-evolution/fase03: o monólito modular com Postgres 18, Redis 8 (cache e busca semântica) e RustFS (capas). Ao fim dela, cadastrar, editar ou excluir um livro não espera mais o Gemini: a requisição grava no Postgres, publica uma tarefa numa fila e responde. Um processo à parte, o worker, consome a fila e atualiza o índice semântico.

O exemplo está em .docs/aulas/filas/exemplo-filas/, com um compose próprio (a fila na porta 6400 e a página em 3300), que não conflita com o do projeto. Os dois estão na branch saas-evolution/fase04, junto deste tutorial.

O que doeu

Abra backend/src/modules/catalog/features/create-book/createBook.ts. Depois do COMMIT, o caso de uso faz await syncBookIndex([book.id], integration). Dentro dele, o livro vira texto, o texto vai para a API do Gemini e volta como vetor. O usuário só recebe o 201 quando o Gemini responde.

  • Gemini lento: o cadastro fica lento junto. Num dia ruim do provedor, segundos para salvar uma linha no banco.
  • Gemini fora do ar ou com limite de cota estourado: syncBookIndex engole o erro (de propósito, para não derrubar o cadastro) e o livro fica fora do índice até a próxima reconciliação, que só roda quando a aplicação reconecta ao Redis.
  • Editar um livro (UC03) e excluir (UC04) passam pelo mesmo caminho.

É o problema clássico de colocar um serviço de terceiros no caminho do usuário: a falha dele vira a sua. A resposta desta aula separa quem pede de quem executa. A aplicação grava, publica a tarefa e responde; o worker processa quando pode e tenta de novo quando falha.

Por que não um void syncBookIndex(...) sem await? A requisição voltaria logo, mas o trabalho continuaria no mesmo processo, sem registro em lugar nenhum. Se o contêiner reiniciar no meio, a tarefa some. Se o Gemini falhar, ninguém tenta de novo. A fila guarda a tarefa fora do processo, com volume, até alguém confirmar que ela foi feita.

01

A fila no compose

Uma fila precisa de três coisas: guardar mensagens na ordem em que chegam, entregar cada uma a quem vai processar e lembrar quais ainda não foram confirmadas. O Redis tem uma estrutura feita para isso, o stream: um log só de acréscimos, em que cada entrada recebe um id crescente (1795105321094-0: milissegundos e sequência). Por cima do stream, um grupo de consumidores divide as entradas entre vários workers e guarda, para cada entrada entregue, quem a recebeu e quantas vezes.

Já usamos o Redis 8, então não há software novo. Mas a fila não vai para o Redis que já existe. Compare os papéis:

ServiçoO que guardaVolume?Sem memória…

Mesmo software, duas configurações opostas. Misturar os dois papéis num só Redis obrigaria o cache a ganhar volume, ou a fila a perder o dela. Separados, cada um tem a regra que o seu dado pede: o cache continua descartável, como a fase02 ensinou.

Publicar e consumir

O módulo da fila fica em backend/src/infrastructure, ao lado do redis.ts e do storage.ts: é infraestrutura compartilhada, e cada tarefa diz no nome do stream qual módulo é o dono dela. Ele usa só seis comandos do Redis:

ComandoQuem usaO que faz
XADDa aplicaçãoacrescenta uma mensagem ao stream e devolve o id dela
XGROUP CREATEo worker, ao subircria o grupo workers; começa do 0 para ler também o que chegou antes
XREADGROUPo workerentrega mensagens novas (>) a este worker; com BLOCK, espera até chegar alguma
XACKo workerconfirma: a mensagem sai da lista de pendentes
XPENDINGo workerlista as pendentes paradas há muito tempo e quantas vezes cada uma já foi entregue
XCLAIMo workerassume uma pendente de outro worker (ou de si mesmo) para tentar de novo

A regra que amarra tudo: só o XACK tira a mensagem da lista de pendentes. Se o worker falha, ou cai no meio, a mensagem continua lá, e alguém a pega de novo depois de um tempo. A entrega é pelo menos uma vez: uma tarefa pode rodar duas vezes (o worker indexou, mas caiu antes do XACK), nunca zero. Por isso toda tarefa tem de ser segura para repetir.

O módulo da fila

Crie backend/src/infrastructure/queue.ts:

tsbackend/src/infrastructure/queue.ts
import type { RedisClient } from "bun";
import { createRedis, ready } from "./redis";

/**
 * A fila mora num Redis só dela (o serviço fila do compose), com volume: ao
 * contrário do cache, o que está ali é trabalho que ainda não foi feito. Sem
 * QUEUE_URL o cliente é null, e cada caso de uso faz o trabalho na hora, dentro
 * da requisição, como era antes desta aula.
 */
export const queue: RedisClient | null = process.env.QUEUE_URL ? createRedis(process.env.QUEUE_URL) : null;

/** Um grupo só: cada mensagem é entregue a UM dos workers do grupo. */
const GROUP = "workers";

/** A fila não é arquivo: cada stream guarda até umas 10 mil mensagens. */
const MAX_LENGTH = "10000";

/** Uma tarefa: o stream de onde ela vem e o que fazer com cada mensagem. */
export type Job<T = any> = {
  /** a chave do stream; o primeiro trecho diz o módulo dono, como toda chave do Redis */
  stream: string;
  /** lança quando falha: sem confirmação, a mensagem volta para a fila */
  handle: (data: T) => Promise<void>;
};

export type WorkerOptions = {
  client: RedisClient;
  /** o nome deste worker dentro do grupo */
  consumer: string;
  /** quanto o XREADGROUP espera por mensagem nova; null não espera */
  blockMs?: number | null;
  /** uma mensagem sem confirmação há este tempo volta a ser entregue */
  retryAfterMs?: number;
  /** na última entrega que falhar, a mensagem vai para a fila de mortas */
  maxDeliveries?: number;
};

type Settings = Required<WorkerOptions>;
type Entry = [id: string, fields: string[]];

const DEFAULTS = { blockMs: 5000, retryAfterMs: 10_000, maxDeliveries: 5 };

/** Onde ficam as mensagens que esgotaram as tentativas, para alguém olhar. */
export function deadLetterStream(stream: string): string {
  return `${stream}:mortas`;
}

/**
 * Publica a tarefa e devolve o id da mensagem; null quando não há fila ou ela
 * não respondeu. A mensagem leva só identificadores, nunca o objeto inteiro:
 * quando o worker for trabalhar, ele lê o estado atual no Postgres.
 */
export async function enqueue(stream: string, data: unknown, client: RedisClient | null = queue): Promise<string | null> {
  if (!client) return null;
  try {
    await ready(client);
    return await client.send("XADD", [stream, "MAXLEN", "~", MAX_LENGTH, "*", "dados", JSON.stringify(data)]) as string;
  } catch (error) {
    console.warn("Fila indisponível:", (error as Error).message);
    return null;
  }
}

/**
 * Cria o grupo de cada stream. Começa do "0", e não do "$": o que foi publicado
 * antes de existir algum worker também é entregue. Criar de novo não é erro.
 */
export async function prepareGroups(jobs: Job[], client: RedisClient): Promise<void> {
  await ready(client);
  for (const job of jobs) {
    try {
      await client.send("XGROUP", ["CREATE", job.stream, GROUP, "0", "MKSTREAM"]);
    } catch (error) {
      if (!/BUSYGROUP/.test((error as Error).message)) throw error;
    }
  }
}

/** Executa uma mensagem. Só o XACK tira a mensagem da lista de pendentes. */
async function run(job: Job, [id, fields]: Entry, deliveries: number, settings: Settings): Promise<void> {
  const { client, maxDeliveries } = settings;
  try {
    await job.handle(JSON.parse(fields[fields.indexOf("dados") + 1] ?? "null"));
    await client.send("XACK", [job.stream, GROUP, id]);
  } catch (error) {
    const reason = (error as Error).message;
    if (deliveries < maxDeliveries) {
      // sem XACK, a mensagem continua pendente e volta depois de retryAfterMs
      console.warn(`Tarefa ${id} de ${job.stream} falhou na tentativa ${deliveries}: ${reason}`);
      return;
    }
    // desistir também é uma decisão: a mensagem sai da fila, mas não some
    await client.send("XADD", [deadLetterStream(job.stream), "*", ...fields, "erro", reason, "origem", id]);
    await client.send("XACK", [job.stream, GROUP, id]);
    console.warn(`Tarefa ${id} de ${job.stream} foi para a fila de mortas depois de ${deliveries} tentativa(s): ${reason}`);
  }
}

/**
 * Pendentes há mais de retryAfterMs: o worker que as recebeu falhou ou caiu sem
 * confirmar. O XPENDING diz quantas vezes cada uma já foi entregue; o XCLAIM
 * passa a mensagem para este worker e confere de novo o tempo parado, então
 * dois workers nunca pegam a mesma.
 */
async function retryStuck(job: Job, settings: Settings): Promise<number> {
  const { client, consumer, retryAfterMs } = settings;
  const stuck = await client.send("XPENDING", [job.stream, GROUP, "IDLE", String(retryAfterMs), "-", "+", "10"]) as [string, string, number, number][];
  let handled = 0;
  for (const [id, , , deliveries] of stuck) {
    const claimed = await client.send("XCLAIM", [job.stream, GROUP, consumer, String(retryAfterMs), id]) as Entry[];
    for (const entry of claimed) {
      await run(job, entry, deliveries + 1, settings);
      handled++;
    }
  }
  return handled;
}

/** Mensagens novas (">"): nunca entregues a ninguém do grupo. */
async function readNew(jobs: Job[], settings: Settings): Promise<number> {
  const { client, consumer, blockMs } = settings;
  const args = ["GROUP", GROUP, consumer, "COUNT", "10"];
  if (blockMs !== null) args.push("BLOCK", String(blockMs));
  args.push("STREAMS", ...jobs.map((job) => job.stream), ...jobs.map(() => ">"));
  // em RESP3, a resposta é um mapa { stream: [[id, campos], ...] }; null quando nada chegou
  const reply = await client.send("XREADGROUP", args) as Record<string, Entry[]> | null;
  if (!reply) return 0;
  let handled = 0;
  for (const job of jobs) {
    for (const entry of reply[job.stream] ?? []) {
      await run(job, entry, 1, settings);
      handled++;
    }
  }
  return handled;
}

/** Uma volta do worker: primeiro as que ficaram pendentes, depois as novas. */
export async function workOnce(jobs: Job[], options: WorkerOptions): Promise<number> {
  const settings = { ...DEFAULTS, ...options } as Settings;
  await ready(settings.client);
  let handled = 0;
  for (const job of jobs) handled += await retryStuck(job, settings);
  return handled + await readNew(jobs, settings);
}

/**
 * O laço do worker. Para no SIGTERM (docker compose stop): fecha a conexão, o
 * que interrompe o XREADGROUP bloqueado. Uma tarefa interrompida no meio não foi
 * confirmada, então outro worker a pega depois: a entrega é "pelo menos uma vez".
 */
export async function work(jobs: Job[], options: WorkerOptions): Promise<void> {
  let running = true;
  const stop = () => {
    running = false;
    options.client.close();
  };
  process.on("SIGTERM", stop);
  process.on("SIGINT", stop);
  while (running) {
    try {
      await prepareGroups(jobs, options.client);
      while (running) await workOnce(jobs, options);
    } catch (error) {
      if (!running) break;
      // fila fora do ar ou recriada sem os grupos: espera e começa de novo
      console.warn("Fila indisponível:", (error as Error).message);
      await Bun.sleep(1000);
    }
  }
}

Pontos para discutir com a turma:

  • enqueue nunca lança. Sem fila, ou com ela fora do ar, devolve null, e quem publicou decide o que fazer. No passo 04, a decisão é fazer o trabalho na hora, como antes.
  • A mensagem leva só ids. Quando o worker for trabalhar, o título pode ter mudado de novo. Ele lê o estado atual no Postgres, a fonte da verdade, em vez de confiar numa cópia guardada na mensagem.
  • MAXLEN ~ 10000. O XACK não apaga a entrada do stream, só a tira das pendentes. Sem um teto, o stream cresceria para sempre. O ~ deixa o Redis cortar em blocos inteiros, o que é mais barato.
  • Tentativas e fila de mortas. Uma mensagem sem confirmação há retryAfterMs (10 s) volta a ser entregue. Na quinta entrega que falhar, ela vai para o stream …:mortas com o erro e o id de origem, e sai da fila. Uma mensagem que nunca vai dar certo (um JSON quebrado, por exemplo) não pode travar a fila nem sumir sem rastro.
  • O XCLAIM confere o tempo parado de novo. Se dois workers acharem a mesma pendente, só um consegue assumi-la.
  • work para no SIGTERM. O docker compose stop manda esse sinal; fechar a conexão interrompe o XREADGROUP bloqueado, e o processo sai sem esperar os 10 s do Docker.

Indexar deixando a falha subir

O syncBookIndex da fase02 nunca lança: dentro da requisição, uma falha do Gemini não pode transformar um cadastro bem-sucedido em erro 500. No worker, é o contrário. Se a falha for engolida, a mensagem recebe o XACK e some, com o livro fora do índice. O worker precisa ver a falha para não confirmar e deixar a fila tentar de novo.

A saída é separar as duas versões: indexBooks faz o trabalho e deixa o erro subir; syncBookIndex chama indexBooks e continua engolindo o erro, para quem ainda faz o trabalho na hora.

A versão que lança

function isUnknownIndex(error: unknown): boolean {
  // Redis 8: "SEARCH_INDEX_NOT_FOUND Index not found"; versões anteriores: "Unknown index name"
  return /index not found|unknown index|no such index/i.test((error as Error).message);

/**
 * Garante que o índice existe para este embedder e diz se precisou criá-lo.
 * Vetores de outro modelo não se comparam com os deste: trocar de modelo apaga o
 * índice junto com os documentos (DD) e começa de novo.
 */
export async function ensureBookIndex(embedder: Embedder, client: RedisClient): Promise<boolean> {
  try {
    if (await client.get(INDEX_MODEL) === embedder.id) {
      await client.send("FT.INFO", [INDEX]);
      return false;
    }
    await client.send("FT.DROPINDEX", [INDEX, "DD"]);
  } catch (error) {
    if (!isUnknownIndex(error)) throw error;
  }
  try {
    await client.send("FT.CREATE", [
      INDEX, "ON", "HASH", "PREFIX", "1", KEY_PREFIX,
      "SCHEMA", "embedding", "VECTOR", "HNSW", "6",
      "TYPE", "FLOAT32", "DIM", String(embedder.dimensions), "DISTANCE_METRIC", "COSINE",
    ]);
  } catch (error) {
    // outra requisição criou o índice ao mesmo tempo
    if (/already exists/i.test((error as Error).message)) return false;
    throw error;
  }
  await client.set(INDEX_MODEL, embedder.id);
  return true;
}

/** O que o modelo lê de cada livro: o título e, para dar contexto, o autor. */
function indexText(title: string, authorName: string | undefined): string {
  return authorName ? `${title} — ${authorName}` : title;
}

async function syncIds(ids: number[], integration: CatalogIntegration, embedder: Embedder | null, client: RedisClient): Promise<IndexResult & { created: boolean }> {
  const result = { indexed: 0, removed: 0, created: false };
  const unique = [...new Set(ids)];
  if (unique.length === 0) return result;
  await ready(client);
  const rows = await sql`SELECT id, titulo AS title, autor_id AS "authorId" FROM livros WHERE id IN ${sql(unique)}` as { id: number; title: string; authorId: number }[];

  // remover não precisa de embedder: o livro saiu do Postgres, sai do índice
  const existing = new Set(rows.map((row) => row.id));
  for (const id of unique) {
    if (!existing.has(id)) result.removed += await client.del(bookIndexKey(id));
  }
  if (!embedder || rows.length === 0) return result;

  result.created = await ensureBookIndex(embedder, client);
  const pending: { id: number; text: string }[] = [];
  for (const row of rows) {
    const text = indexText(row.title, (await integration.author(sql, row.authorId))?.name);
    // só paga o embedding quando o texto mudou ou quando o vetor gravado não tem o
    // tamanho deste modelo: o índice recusa esse vetor em silêncio, e ele ficaria para sempre
    const key = bookIndexKey(row.id);
    const sameText = await client.hget(key, "texto") === text;
    const rightSize = await client.send("HSTRLEN", [key, "embedding"]) === embedder.dimensions * 4;
    if (!sameText || !rightSize) pending.push({ id: row.id, text });
  }
  if (pending.length === 0) return result;

  const vectors = await embedder.embed(pending.map((item) => item.text), "document");
  for (const [i, item] of pending.entries()) {
    const vector = vectors[i]!;
    const blob = Buffer.from(vector.buffer, vector.byteOffset, vector.byteLength);
    // send aceita Buffer em tempo de execução; os tipos do Bun só declaram string
    await client.send("HSET", [bookIndexKey(item.id), "texto", item.text, "embedding", blob as unknown as string]);
  }
  result.indexed = pending.length;
  return result;
}

/**
 * Atualiza o índice para estes livros e deixa a falha subir: é a versão do
 * worker, que tenta de novo mais tarde. Repetir é seguro, porque só paga um
 * embedding novo quando o texto do livro mudou.
 */
export async function indexBooks(ids: number[], integration: CatalogIntegration, embedder: Embedder | null = defaultEmbedder, client: RedisClient | null = redis): Promise<IndexResult> {
  if (!client) return { indexed: 0, removed: 0 };
  const { created, ...result } = await syncIds(ids, integration, embedder, client);
  // índice novo (Redis reiniciado, modelo trocado): os outros livros também precisam entrar
  if (created) void reconcileBookIndex(integration, embedder, client);
  return result;
}

/** Compara o índice inteiro com o Postgres: indexa o que falta e remove o que sobrou. */
export async function reconcileBookIndex(integration: CatalogIntegration, embedder: Embedder | null = defaultEmbedder, client: RedisClient | null = redis): Promise<IndexResult> {
  if (!client) return { indexed: 0, removed: 0 };
  try {
    await ready(client);
    const ids = new Set((await sql`SELECT id FROM livros` as { id: number }[]).map((row) => row.id));
    let cursor = "0";
    do {
      const [next, keys] = await client.scan(cursor, "MATCH", `${KEY_PREFIX}*`, "COUNT", 500);
      cursor = next;
      for (const key of keys) ids.add(Number(key.slice(KEY_PREFIX.length)));
    } while (cursor !== "0");
    const { created, ...result } = await syncIds([...ids], integration, embedder, client);
    return result;
  } catch (error) {
    console.warn("Índice semântico indisponível:", (error as Error).message);
    return { indexed: 0, removed: 0 };
  }
}

/**
 * O Bun conversa em RESP3, e nele o FT.SEARCH responde um mapa
 * ({ results: [{ id, extra_attributes }] }). Em RESP2 a mesma resposta é uma
 * lista plana: [total, chave, [campo, valor], chave, [campo, valor], ...].
 */
export function parseKnnReply(reply: unknown, keyPrefix: string): KnnHit[] {
  const toHit = (key: string, distance: string) => ({ id: Number(key.slice(keyPrefix.length)), distance: Number(distance) });
  if (Array.isArray(reply)) {
    const hits: KnnHit[] = [];
    for (let i = 1; i < reply.length; i += 2) {
      const fields = reply[i + 1] as string[];
      hits.push(toHit(reply[i] as string, fields[fields.indexOf("distancia") + 1]!));
    }
    return hits;
  }
  const { results } = reply as { results: { id: string; extra_attributes: { distancia: string } }[] };
  return results.map((result) => toHit(result.id, result.extra_attributes.distancia));
}

/** O stream da indexação. O primeiro trecho diz o dono, como toda chave do Redis. */
export const BOOK_INDEX_STREAM = redisKey("acervo", "fila", "indice-livros");

/** A mensagem leva só os ids: o worker lê o título e o autor atuais no Postgres. */
type BookIndexTask = { ids: number[] };

/**
 * Depois do COMMIT: pede ao worker que atualize o índice destes livros e volta
 * na hora. Sem fila, ou com ela fora do ar, faz o trabalho aqui mesmo, como
 * antes: mais devagar, mas o livro não fica de fora do índice.
 */
export async function scheduleBookIndex(ids: number[], integration: CatalogIntegration, client: RedisClient | null = queue): Promise<void> {
  const task: BookIndexTask = { ids };
  if (await enqueue(BOOK_INDEX_STREAM, task, client)) return;
  await syncBookIndex(ids, integration);
}

/** A tarefa do lado do worker. Ao contrário de syncBookIndex, aqui a falha sobe: a fila tenta de novo. */
export function bookIndexJob(integration: CatalogIntegration): Job<BookIndexTask> {
  return {
    stream: BOOK_INDEX_STREAM,
    async handle(task) {
      if (!Array.isArray(task?.ids) || !task.ids.every(Number.isInteger)) {
        throw new Error("Tarefa de indexação sem a lista de ids");
      }
      const { indexed, removed } = await indexBooks(task.ids, integration);
      console.log(`Índice semântico: livro(s) ${task.ids.join(", ")}: ${indexed} indexado(s), ${removed} removido(s)`);
    },
  };
}
  • A chave do stream tem dono. redisKey("acervo", "fila", "indice-livros") vira biblioteca:acervo:fila:indice-livros, e o check-boundaries confere o primeiro trecho como em qualquer chave do Redis: nenhum outro módulo publica nessa fila.
  • Sem fila, o trabalho na hora. Se enqueue devolve null (sem QUEUE_URL, como na suíte, ou com a fila fora do ar), scheduleBookIndex chama syncBookIndex: o comportamento da fase03. Fica mais lento, mas o livro não sai do índice. Se a publicação tiver dado certo e só a resposta se perdeu, o livro pode ser indexado duas vezes, o que é seguro (passo 03).
  • handle confere a mensagem. O que vem da fila é dado externo, como o corpo de uma requisição. Uma mensagem sem ids lança, e a fila decide o destino dela.

O worker

O worker não é outro sistema. É o mesmo código, na mesma imagem, com outro ponto de entrada: em vez de src/main.ts, que abre a porta 3000, ele roda src/worker.ts, que fica lendo a fila. Mesmo repositório, mesmo banco, mesmos módulos. Só o processo é outro, e por isso o trabalho lento não divide CPU nem memória com quem atende o usuário.

O que cada passo ensinou

PassoA ideia que fica
00um serviço de terceiros no caminho do usuário transforma a falha dele na sua
01a fila é estado: tem volume e não descarta nada. Mesmo software do cache, regra oposta, contêiner separado

03na requisição, a falha derivada é engolida; no worker, ela sobe para a fila tentar de novo. Toda tarefa precisa ser segura para repetir

Em produção

  • Vigie o lag e a fila de mortas. Um worker parado não derruba o produto, e é exatamente por isso que ninguém percebe. O alerta é sobre o sintoma: a fila crescendo, ou uma mensagem nova em …:mortas.
  • Fila gerenciada. Num provedor de nuvem, o serviço fila vira um Redis gerenciado com persistência, ou um broker dedicado (Amazon SQS, RabbitMQ, NATS JetStream). Os conceitos desta aula são os mesmos: confirmação, nova entrega, limite de tentativas e fila de mortas.
  • Workers escalam pelo lag. Em vez de um número fixo, o orquestrador sobe mais workers quando a fila cresce e desliga quando ela esvazia.
  • Versão nova lendo mensagem velha. No deploy, o worker novo pode receber mensagens publicadas pelo código antigo. Mudar o formato de uma tarefa pede uma janela em que o worker entenda os dois.

O que ficou de fora

  • Outbox. O XADD acontece depois do COMMIT. Se a aplicação cair entre um e outro, a tarefa não é publicada. Para a indexação, a reconciliação cobre o buraco: tudo no índice pode ser recalculado a partir do Postgres. Entra quando aparecer a primeira tarefa que não dá para recalcular, como um e-mail: aí a tarefa é gravada numa tabela na mesma transação do dado, e um processo a publica depois.
  • Espera crescente entre tentativas. Aqui toda nova tentativa espera os mesmos 10 s. Com espera crescente (10 s, 20 s, 40 s…), um provedor fora do ar por meia hora não recebe uma rajada a cada 10 segundos. Entra quando as tentativas começarem a atrapalhar quem está tentando se recuperar.
  • Tarefas periódicas. A reconciliação do índice e a varredura de capas órfãs da fase03 cabem no worker como tarefas de horário. Com dois workers, precisam de uma trava para não rodar duas vezes.
  • A edição de autor (UC07). Renomear um autor ainda reindexa todos os livros dele dentro da requisição, pelo syncAuthorBookIndex. É a próxima candidata natural a passar pela fila.

A atividade

Agora é a sua vez: a atividade (.docs/atividades/atividade-fila.html) leva a fila para a Circulação. Registrar um empréstimo (UC19) passa a mandar ao leitor um comprovante por e-mail, e quem envia é o worker. O provedor de e-mail de desenvolvimento (o Mailpit), o texto do comprovante e os testes de aceite estão prontos; publicar a tarefa, processá-la uma vez só e ligá-la ao worker ficam com você. Há um cuidado a mais: um e-mail enviado não se desfaz nem se recalcula, e a fila entrega cada mensagem pelo menos uma vez.

A fila entrou ao lado do Postgres e do Redis sem tomar o lugar de nenhum deles. O Postgres continua respondendo o que existe; o índice continua sendo uma cópia que pode ser recalculada; e a fila guarda só o que ainda falta fazer, até alguém confirmar que fez.
